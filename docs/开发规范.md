# 开发规范（Git 工作流）

> 本文件约束本仓库的所有代码改动流程。**对人和 AI 协作者同样生效。**

## 1. 分支规则

1. **一切改动必须新建分支**，包括代码、配置和一切文档修改。
2. **禁止直接提交 main**（`git commit` / `git push` 到 main 均不允许），main 只接受 PR 合并。
   - 例外：仓库初始化时的首次导入提交。
3. main 分支任何时刻保持可构建、可运行。

### 分支命名

格式：`<类型>/<简短英文或拼音描述>`，与下文 commit type 对应：

| 类型 | 用途 | 示例 |
|---|---|---|
| `feat/` | 新功能 | `feat/sse-streaming` |
| `fix/` | 缺陷修复 | `fix/session-cache-rebuild` |
| `docs/` | 文档 | `docs/dev-spec` |
| `chore/` | 构建、依赖、配置等杂项 | `chore/upgrade-spring-ai` |

### 改动粒度（2026-09-26 补充，同日二次订正）

**不要为每个小细节单开 PR；也绝不直接提交 main。** 一切工作都发生在分支上。

- **小改动**（一句话能说清、回滚无风险：文档微调、错别字、注释、单文件小修等）：照常切分支写，**攒够几个 bug/小改动后合并成一个 PR** 提交，不逐个开 PR。
- **功能/多文件/行为变更**：单独分支 + PR。
- 拿不准时按大改动处理。纪律红线：**任何 commit 都不得出现在 main 上**。

## 2. Commit 格式

```
type：中文描述
```

- 冒号使用**全角冒号 `：`**，冒号后空一格（可选）再写中文描述。
- 描述写清楚「做了什么」，一句话说不完时在正文空行后补充细节。

常用 type：

| type | 含义 |
|---|---|
| `feat` | 新功能 |
| `fix` | 修 bug |
| `docs` | 只改文档 |
| `style` | 格式调整（不影响逻辑） |
| `refactor` | 重构（既非新增也非修复） |
| `test` | 测试相关 |
| `chore` | 构建、依赖、配置、杂务 |

示例：

```
feat：新增 SSE 流式回复接口
fix：修复 Redis 宕机后会话上下文重建失败的问题
docs：补充开发规范
```

## 3. 合并流程（PR）

1. 改动完成并自测通过后，推送分支到 GitHub；
2. 在 GitHub 上发起 **Pull Request**（目标分支 `main`），标题可用 commit 同款格式；
3. PR 合并回 main 后删除功能分支。

### 完整示例

```bash
# 1) 从最新 main 拉出开发分支
git checkout main && git pull
git checkout -b feat/sse-streaming

# 2) 开发、提交（禁止在 main 上做这一步）
git add <文件>
git commit -m "feat：新增 SSE 流式回复接口"

# 3) 推送并发起 PR
git push -u origin feat/sse-streaming
gh pr create --base main --fill

# 4) 合并后清理
gh pr merge --squash --delete-branch
```
