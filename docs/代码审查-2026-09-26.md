## 3. 本次修复说明（#1 / #2 / #4 / #3）

### #1 超限上传返回 500（P1）

- **根因**：Spring multipart 层在请求进入 Controller 前抛 `MaxUploadSizeExceededException`，`GlobalExceptionHandler` 无对应 handler，落入 `Exception` 兜底返回 500；`ResumeService.upload` 里的 10MB 校验永远执行不到。
- **修复**：新增 `@ExceptionHandler(MaxUploadSizeExceededException.class)` 返回 400 + 可读文案；同时 `server.tomcat.max-swallow-size` 调到 12MB（与 max-request-size 对齐）——默认 2MB 时超限较多的上传会被 Tomcat 直接断连，客户端只能看到"网络异常"而收不到 400 响应。
- **遗留**：远超限制的巨型文件（>22MB 左右）仍会断连（前端显示网络异常），属 Tomcat 防护语义，保留。

### #2 RerankClient 无超时（P1）

- **根因**：`RestClient.builder()` 默认请求工厂无连接/读超时；rerank 在生成主链路同步调用（assembleInput → 检索 → 重排），DashScope 连接挂起时占住 agentGenExecutor 线程直到资源耗尽，`rerank()` 的 try-catch 接不住"不返回"的调用，"快速降级"承诺失效。
- **修复**：构造器为 RestClient 配置显式请求工厂：连接超时 3s、读超时 10s（gte-rerank 20 文档实测秒级，余量充足）。超时抛异常 → 既有 catch → 降级向量序。

### #3 删向量 topK 封顶漏删（P2）

- **根因**：`deleteResumeVectors` 用 `similaritySearch(topK=200)` 找出待删文档再删除；SimpleVectorStore 无按 filter 删除能力，单次检索最多返回 200 条，超限部分成孤儿向量（还可能被后续引用溯源展示）。
- **修复**：循环"检索→删除"直到返回不足一页（<200 即已删净），每轮删除后下一轮必然更少，保证终止。

### #4 生成线程池扩容语义（P2）

- **根因**：JDK `ThreadPoolExecutor` 是"队列满才从 core 扩到 max"。LLM 生成为长任务，core=4/max=8/queue=50 下实际并发恒为 4，max=8 形同虚设，排队用户最深可达 50 才触发拒绝。
- **修复**：`corePoolSize` 提到与 max 相同（8），启动即满配并发；queue=50 与 409 拒绝语义保持不变。

## 4. 有意取舍（审查确认合理，不动）

- **SSE 锁内网络发送**（#8）：本地 1-2 订阅者、小负载，锁内阻塞发送代价可忽略（代码注释已自证）；多人部署时需重新评估。
- **Redis 缓存非原子**（#14）：库为唯一事实来源，缓存仅是加速层，自愈机制（cacheHasGap/rebuildWindow）完备。
- **消息不逻辑删除**：评估报告依赖完整记录，uk_session_seq 依赖序号连续——设计约束，注释已说明。
- **SimpleVectorStore**：千级 chunk 足够，接口统一可平移 RedisVectorStore/pgvector。
- **XSS 面**：LLM 输出经 Vue 模板插值渲染（自动转义），当前安全；**将来若引入 markdown 渲染必须 sanitize**，模型输出不可信。
